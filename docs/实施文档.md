## 1. 范围

**要做**

1. 本机服务，提供网页和接口。
2. 模版库：维护品类、款式、白底图、自定义模版和提示词；支持导入导出。
3. 持久化任务队列，五步流水线：识别品类 → 提取素材 → 生成主图 → 信息识别 → 空白图。
4. 「需处理」区、单张从任意一步重做、断点续跑。
5. 输出文件和识别信息 CSV。
6. Mac 和 Windows 的双击启动脚本。
7. 模拟中转站，加上自动化测试。

**不做**

- 连接知识库平台。
- 多用户、局域网共享。
- 本地像素擦除（空白图完全由 AI 重新生成）。
- 图片编辑器。

## 3. 数据结构

所有结构在 `server/src` 里用 zod 定义，类型由 zod 推导；前端复制一份类型（`web/src/types.ts`）。

### 3.1 模版库 `library/library.json`

```ts
type Library = {
  version: 2                       // v1（模版挂在品类上）启动/导入时自动升级，把模版复制给每个款式
  defaults: {
    extractPrompt: string          // ② 全局默认，支持占位符
    pastePrompt: string            // ③ 默认模版「贴图」
  }
  categories: Category[]           // 数组顺序就是显示顺序
  whiteChecks: Record<hash, WhiteShape>   // 2026-10-27：白底图本地图形检测结果，按图片 hash 存；旧库没有就是 {}，不升版本（见 §15.3）
}
type Category = {
  id: string                       // "c_" + 8 位随机
  name: string                     // 1–20 字，不能重名
  hint: string                     // 给 AI 的识别说明，可为空
  extractPrompt: string | null     // null = 用全局默认
  styles: Style[]                  // 至少 1 个；单款式品类的 name 为 ''
}
type Style = {
  id: string                       // "s_" + 8 位
  name: string                     // 可为空串（单款式）
  ratio: string                    // 图案本身的宽:高，正整数比
  whiteImage: string | null        // 图片 hash（见 3.2）
  activeTemplate: 'default' | string   // 'default' 或本款式 templates[].id
  templates: Template[]            // 自定义模版属于款式，款式之间互不影响
  pasteMode: 'auto' | 'local' | 'ai'   // 2026-10-27：默认模版的贴图方式，默认 auto（见 §15.3）
}
type Template = {
  id: string                       // "t_" + 8 位，款式内唯一
  name: string
  prompt: string
  image: string | null             // 参考图，可缺
  canvasRatio: string | null       // 没有参考图时主图画布比例；null 跟款式比例
}
```

初始内容（库文件不存在时写入；2026-10-27 换成新默认，见 §15.2、§15.3。库里存的和旧默认一字不差时，启动/导入时自动换成新的，改过的不动）：

- `defaults.extractPrompt`：
  > 这是一张{品类}商品图。只要商品印刷面上的图案部分，转成正面的平面设计稿并高清处理，图案四边铺满画布，比例 {比例}。
- `defaults.pastePrompt`：
  > 把素材图像一张不透明的贴纸一样覆盖在白底图商品的整个印刷面上，贴合原有透视：印刷面以内只看得到素材图，一直铺到商品轮廓，不留白边、不超出轮廓。商品原来的材质、颜色、纹理在任何地方都不能透出来，素材图里白色或浅色的部分也一样。保留安装孔等实体结构。直接使用原素材，不重绘，不修改文字、图案和排版。商品的形状、位置、取景、背景和阴影与白底图完全一致，只完成贴图，不做其他改动。
- `categories: []`（品类由用户自己添加）。

**占位符**（`prompts/placeholders.ts`）：`{品类}`、`{款式}`、`{比例}`。三个占位符在提取提示词和所有模版提示词里都会替换。款式为空串时，`{款式}` 替换成空串，并把多余的「·」和空格清理掉。

### 3.2 模版库图片 `library/images/<sha256>.<ext>`

- 只接收 PNG、JPG、WebP，其他格式拒收。同一张图只存一份（按 sha256）。
- 同时生成缩略图 `library/images/thumbs/<sha256>.webp`（长边 320）。
- **清理孤儿文件**只在两个时机做：服务启动时、导入完成后。凡是 `library.json` 没有引用的文件都删掉。日常保存时不删。
- `library/store.ts` 用互斥锁串行化所有写操作，写盘必须原子写（见 3.5）。

### 3.3 设置 `data/settings.json`

```ts

  image:    { baseUrl: string; apiKey: string; model: string; concurrency: number; timeoutSec: number; sendFidelity: boolean }
  analysis: { baseUrl: string; apiKey: string; model: string; concurrency: number; timeoutSec: number }
  outputDir: string          // 默认 ~/Downloads（~ 在运行时展开），每批图一个文件夹「主图生成-日期[-序号]」（§15.1）
  routeThreshold: number     // 默认 0.7

```

- 默认值：
  - `image`：model `gpt-image-2`，并发 2，超时 300 秒，`sendFidelity` 为 true。
  - `analysis`：model `gpt-5.5`，并发 3，超时 60 秒。

### 3.4 任务 `data/jobs/<jobId>/job.json`

每个任务一个目录，图片文件和 `job.json` 放在一起：`source.<ext>`、`pattern.png`、`main.png`、`blank.png`，以及 `thumbs/*.webp`。

```ts
type StepState = 'pending' | 'running' | 'done' | 'skipped' | 'failed'
type Job = {
  id: string                       // 时间戳 base36 + 4 位随机，按字典序即创建顺序
  createdAt: string
  order: number                    // 调度顺序；挪到队尾 = 当前最大值 + 1
  source: { file: string; originalName: string; width: number; height: number; sha256: string }
  outputDay: string                // YYYY-MM-DD（创建当天）
  outputFolder: string             // 输出文件夹名，同一批共用，规则见 §15.1；旧任务读入时补成「主图生成-<outputDay>」
  outputBase: string               // 原文件名去扩展名；同一天同一品类目录下重名时加 _2、_3
  route: null | {
    categoryId: string; styleId: string
    categoryName: string; styleName: string; ratio: string   // 快照，品类被改名或删除后仍能显示
    confidence: number | null      // 手动指定时为 null
    reason: string | null
    manual: boolean
  }
  plan: null | {                   // ② 开始时解析一次；③ 直接用它
    extractPrompt: string          // 占位符已替换
    main: {
      templateId: 'default' | string; templateName: string
      prompt: string               // 占位符已替换
      image: null | { role: '白底图' | '参考图'; hash: string }
    }
  }
  steps: [StepRecord, StepRecord, StepRecord, StepRecord, StepRecord]
  info: null | {
    scene: string; keywords: string[]; customizable: string[]
    blankItems: string[]           // 中文，已经过兜底和拦截处理
    blankItemsEn: string[]
  }
  attention: null | {
    kind: 'nomatch' | 'nowhite' | 'failed' | 'refused'
    step: 0 | 1 | 2 | 3 | 4
    message: string                // 给人看的中文原因
    guess?: string                 // nomatch 时 AI 猜的品类名
    at: string
  }
  override: null | { step: number; prompt: string }   // 单张重做时临时改的提示词，只用一次
}
type StepRecord = {
  state: StepState
  attempts: number
  startedAt?: string; endedAt?: string
  error?: string
  snapshot?: {                     // 实际发出去的内容，详情面板据此展示
    images: { no: number; role: string; sha256: string }[]
    prefix: string; prompt: string
    model: string; size?: string; params?: Record<string, unknown>
  }
  output?: string                  // 任务目录里的文件名
}
```

**状态流转**（白名单，写在 `store/jobs.ts`，其他地方不能直接改 `state`）：

```
pending → running
running → done | skipped | failed | pending   (pending 用于：重启复位、429 退回、401 暂停退回)
done | skipped | failed → pending              (只能通过重做或重试)
```

一张图同一时刻最多有一个步骤处于 `running`。

### 3.5 原子写

`store/atomic.ts`：先写 `<file>.tmp-<rand>`，再 `fsync`，最后 `rename` 覆盖原文件。在 Windows 上 `rename` 遇到 `EPERM` 或 `EBUSY` 时，间隔 50ms 重试，最多 5 次。

### 4.4 SSE 事件

`events/bus.ts` 是一个进程内的 EventEmitter，`/api/events` 订阅它并转发给页面。

- `job`：`{ job }`，推送完整记录，任何字段变化都发。
- `job-removed`：`{ id }`。
- `queue`：同 `GET /queue` 的返回。
- `library`：`{ library, checks }`。
- `toast`：`{ level: 'info'|'warn'|'error', message }`，用于「3 张等白底图的任务已回到队列」这类提示。

每 20 秒发一次注释行 `: ping`，防止连接被断开。页面断线后自动重连，重连后先 `GET /jobs` 和 `GET /library` 拉一次全量。

## 5. AI 调用（`server/src/ai/`）

### 5.1 HTTP 与错误分类

`http.ts`：基于全局 `fetch` 和 `AbortController` 实现超时；单次请求超时取设置里的 `timeoutSec`。

`errors.ts` 把所有失败归成一个 `AiError`，其中 `type` 取下表之一：

| type | 判定 | 后续处理 |
|---|---|---|
| `network` | fetch 抛异常、超时、连接被重置 | 可重试 |
| `server` | HTTP 5xx、408、425 | 可重试 |
| `badImage` | 返回内容里取不到图片，或 sharp 解码失败 | 可重试 |
| `rateLimit` | HTTP 429 | 见 5.3 |
| `auth` | HTTP 401、403 | 暂停该类接口的所有任务 |
| `unknownParam` | HTTP 400，且错误信息同时满足：匹配 `/unknown\|unrecognized\|unsupported\|not support\|invalid\|extra/i`，并且包含 `input_fidelity` 或 `quality` | 去掉这两个参数立即重发 |
| `refused` | HTTP 400/422，错误信息匹配 `/content[_ ]?policy\|safety\|moderation\|rejected\|violat\|违规\|敏感/i` | 不重试 |
| `badOutput` | 分析结果解析不出 JSON，或 zod 校验失败 | 见 5.4 |
| `client` | 其余 4xx | 不重试 |

错误信息最多截取 300 字，并去掉其中的 Key。

### 5.2 重试

`retry.ts`：只有可重试的类型才重试。间隔依次为 **3、6、10、15 秒**，所以一次步骤最多尝试 5 次。每次尝试都记进 `StepRecord.attempts`。重试期间，这个任务一直占着自己的并发位置。

### 5.3 限流与降级

- **429**：等待 `Retry-After` 指定的秒数（取不到时等 20 秒，最多 120 秒），**不计入**重试次数。同时把该类接口的并发上限临时减 1（最低到 1）；连续 2 分钟没有再出现 429，就恢复到设置值。限流逻辑写在 `limiter.ts`。
- **unknownParam**：在同一次尝试内去掉 `quality` 和 `input_fidelity` 重发，并把 `settings.image.sendFidelity` 写成 false，之后的请求都不再带这两个参数。设置页上显示「中转站不支持保真参数，已自动关闭」，并提供重新开启的开关。
- **auth**：该步骤退回 pending；队列设置 `paused = { by:'auth', kind, message:'生图接口 Key 无效或无权限' }`。调度器不再派发这一类步骤，另一类照常运行。用户保存设置后自动解除。

### 5.4 生图客户端 `imageClient.ts`

```
POST {image.baseUrl}/images/edits   multipart/form-data
Authorization: Bearer {key}
字段：
  model            settings.image.model
  prompt           prefix + prompt
  image            只有一张图时用这个字段名
  image[]          多张图时用这个字段名，按顺序依次追加
  n=1
  size             1536x1024 | 1024x1536 | 1024x1024
  quality=high, input_fidelity=high   （sendFidelity 为 true 时才带）
```

返回结果兼容三种形式，按顺序尝试：

1. `Content-Type` 是 `image/*`：响应体就是图片。
2. JSON 里有 `data[0].b64_json`：解码 base64。
3. JSON 里有 `data[0].url`：再 GET 一次取图（超时 60 秒）。

拿到图片后先用 sharp 读取元信息，确认能解码；解码失败归为 `badImage`。

### 5.5 分析客户端 `chatClient.ts`

```
POST {analysis.baseUrl}/chat/completions
{ model, temperature: 0,
  messages: [ {role:'system', content: SYSTEM},
              {role:'user', content:[ {type:'text', text: USER}, {type:'image_url', image_url:{url:'data:image/jpeg;base64,...'}} ]} ] }
```

- `json.ts`：先去掉 markdown 代码围栏，再从第一个 `{` 开始做括号配对，取出第一个完整的 JSON 对象，然后交给 zod 校验。
- 校验失败时，在 user 消息后追加一条「只输出符合格式的 JSON 对象，不要任何其他文字」，再问一次；第二次仍然失败，记为 `badOutput`，不再重试。
- 送去分析的图片，先用 `shrinkForAnalysis` 处理（见 §8）。

## 6. 调度与流水线

### 6.1 调度器 `scheduler/scheduler.ts`

```
kindOf(step) = step ∈ {0,3} ? 'analysis' : 'image'

tick():
  if paused.by === 'user': return
  for job in jobs sorted by order:
    if job.attention: continue
    i = 第一个 state 不是 done/skipped 的步骤；没有就跳过（任务已完成）
    if steps[i].state !== 'pending': continue        // running 或 failed
    k = kindOf(i)
    if paused.by === 'auth' && paused.kind === k: continue
    if busy[k] >= limit[k]: continue
    start(job, i)    // 同步把状态置为 running、busy[k]++，异步执行处理器
```

- **什么时候 tick**：服务启动、有任务入队、步骤结束、模版库变更、设置保存、继续队列、重做或重试。tick 要做防重入，可以用一个 microtask 合并多次触发。
- **启动复位**：服务启动时，把所有 `running` 改回 `pending`（attempts 不变），然后 tick 一次。
- **步骤处理器的约定**：签名为 `(job, ctx) => Promise<StepResult>`。每个处理器只读前面步骤的产出，只写自己的 `output`、`snapshot`，以及 `route`、`plan`、`info` 中归自己管的那一块。不要在处理器里改调度相关的字段。
- **结果处理**：
  - 成功：当前步骤置为 `done`（或 `skipped`），写盘，发 `job` 事件，然后 tick。
  - 失败：按错误类型转成 `attention`，或者退回 `pending`（429、auth 两种情况）。

### 6.2 五个步骤

#### ① 识别品类 `step0Route.ts`

- 模版库里一个品类都没有时：直接设为 `attention nomatch`，message 为「模版库还没有品类，请先到模版库添加」。不调用 AI。
- 提示词由 `prompts/route.ts` 每次根据当前模版库现场生成：

  **SYSTEM**
  ```
  你是电商商品图分类助手。给你一张竞品商品图和一份品类清单，判断图中商品属于清单中的哪个品类、哪个款式。只输出一个 JSON 对象，不要输出任何其他文字：
  {"category_id": "清单中的品类 id；清单里没有对应品类时为 null", "style_id": "该品类下的款式 id；无法判断时为 null", "confidence": 0 到 1 之间的小数, "reason": "一句话中文判断理由", "guess": "图中商品的中文品类名，无论是否匹配都必须填写"}
  规则：
  1. 只能从清单中选择，不得编造 id。看不清或清单中没有对应品类时 category_id 填 null。
  2. 款式按商品印刷面的形状和方向判断（例如横版/竖版看印刷面的宽高），不要按整张照片的宽高判断。
  3. confidence 表示你对品类判断的把握，不要习惯性给高分。
  品类清单：
  {清单}
  ```

  `{清单}` 每个品类占一行，格式为：`- 品类 id: c_xxx｜名称: 相框｜识别说明: 挂墙帆布画…｜款式: s_a 横版（比例 3:2）；s_b 竖版（比例 2:3）`。单款式品类写成 `款式: s_a （单款式，比例 1:1）`。

  **USER**：`请判断这张商品图属于清单中的哪个品类和款式。`

- **代码校验**，按顺序执行：
  1. `category_id` 不在清单里，或者为 null：nomatch，message 为「AI 判断是「{guess}」，模版库里没有这个品类」。
  2. 品类只有一个款式：直接用这个款式，忽略 `style_id`。
  3. 品类有多个款式，但 `style_id` 无效：nomatch，message 为「认出是{品类}，但判断不了款式」。
  4. `confidence` 低于 `routeThreshold`：nomatch，message 为「AI 认为是「{品类·款式}」，但把握只有 0.xx」。
- 以上任何一种 nomatch 都要把 `guess` 带上。
- 校验通过：写入 `route`（`manual: false`），① 置为 `done`。

#### 解析计划 `pipeline/plan.ts`

② 开始前调用 `resolvePlan(job, library)`。下面三种情况，也要用当前模版库重新解析：

- 从 ① 或 ② 重做；
- 从 ③ 重做；
- nowhite 解除后重新开始。

解析步骤：

1. 按 `route.categoryId` 和 `route.styleId` 查找品类和款式。找不到时，转 nomatch，message 为「品类或款式已被删除」。
2. 提取提示词：用品类的 `extractPrompt`；为空时用 `defaults.extractPrompt`。再替换占位符。
3. 主图模版：按款式的 `activeTemplate` 取本款式的模版；找不到时回退到 `'default'`。
   - **默认模版**：`image` 设为该款式的白底图，角色是「白底图」；`prompt` 用 `pastePrompt`。白底图为空时，转 `attention nowhite`，step 记为 1，message 为「「{品类·款式}」还没有白底图，上传后这张图会自动继续」。
   - **自定义模版**：`image` 取模版的 `image`，角色是「参考图」；这一项可以为空，为空就不发参考图。`prompt` 用模版的提示词，并替换占位符。
4. 把结果写进 `job.plan`。

`library/recipe.ts` 与流水线 ③ **共用** `buildMainRequest(planMain, ratio)`。模版库页面的配方预览调用的就是这个函数。界面上显示什么，就发送什么，这条必须保证。

#### ② 提取素材 `step1Extract.ts`

- 发送的图片：只有竞品图一张。
- `prefix`：`prompts/canvas.ts` 生成的 `[Canvas: {ratio} {orientation} format] ` 加上「第一张图片是竞品商品图。」，再换行。`ratio` 和 `size` 都由款式比例算出。
- `prompt`：`plan.extractPrompt`。如果 `override.step === 1`，改用 override 的内容，用完就清掉。
- 产出 `pattern.png`：统一转成 PNG，**不裁剪**。
- 2026-10-27：前置句后面固定加一段英文保真约束；提取完再做素材图验收，见 §15.2。

#### ③ 生成主图 `step2Main.ts`

由 `buildMainRequest` 生成请求：

- 发送的图片：`[plan.main.image?, pattern.png]`。没有白底图或参考图时，只发素材图。
- `prefix`：画布描述 + 角色声明。角色声明按实际发送的图片编号，例如：
  - 「第一张图片是白底图，第二张图片是素材图。」
  - 「第一张图片是参考图，第二张图片是素材图。」
  - 「第一张图片是素材图。」
- 画布比例和 `size`：有第一张图（白底图或参考图）时，按它的实际宽高算；没有时，按款式比例算。
- 2026-10-27：默认模版分「本地合成 / AI 贴图」两种方式，AI 贴图时前置句后面固定加一段英文约束，见 §15.3。自定义模版不变。
- 产出依次做以下处理，最后写成 `main.png`：
  1. `capEdge(2000)`；
  2. 设置里开了 `padSquare` 时，执行 `padSquare()`：只在两侧或上下补白边，原图像素不缩放；
  3. `capBytes(9.5MB)`。

#### ④ 信息识别 `step3Info.ts`

发送的是 `main.png`，先经过 `shrinkForAnalysis` 处理。提示词沿用旧版，原文如下：

**SYSTEM**
```
你是亚马逊电商主图分析助手。请先判断图中的产品属于什么品类（例如 throw blanket / beach towel / mug / t-shirt / garden flag 等），再基于这个品类输出以下四项信息的 JSON，不要输出任何 JSON 之外的文字：
{
  "scene": "[图中场景的一句话中文描述，必须包含产品品类，例如节日/送礼/日常使用等场景]",
  "keywords": ["[第一个必须是英文品类核心词，如 throw blanket]", "[次重要的英文搜索关键词]", "[共 3 到 5 个，按重要性从高到低排序，供亚马逊 listing 使用]"],
  "customizable": ["[图中可替换元素的简短名词，2-4个字，例如：名字、照片、宠物形象，不要写成一句话描述]", "[另一个可替换元素的简短名词]"],
```

**USER**：`请分析这张产品主图，先判断产品品类，再按要求输出 JSON。`

校验规则：

- `keywords` 忽略大小写去重后，截取前 5 个，至少要有 1 个。

### 6.3 重做、重试、处理

**`redo(step N, prompt?, categoryId?, styleId?)`**

- 只允许对 `done`、`skipped`、`failed` 状态的步骤重做。
- 步骤 N 及之后的所有步骤：`state` 改为 `pending`，`attempts` 清零，`output`、`snapshot`、`error` 清空，对应的文件删除。已经输出到输出目录的文件，等新结果生成后再覆盖。
- 按 N 分别处理：
  - N = 0 且带了 `categoryId`：直接写入 `route`（`manual: true`），① 置为 `done`，然后从 ② 开始。
  - N ≤ 1：清空 `plan`，在 ② 开始时重新解析。
  - N = 2：只重新解析 `plan.main`。
- 带了 `prompt` 时，写入 `override = { step: N, prompt }`。
- 清掉 `attention`。**队列位置保持不变**，所以用户主动重做的图会优先处理。

**`resolve` / `create-category` / `retry`**：都是处理完后**挪到队尾**。这样「需处理」里的图不会插到别的图前面。

### 6.4 模版库变更后自动放行

收到 `library` 事件时：

1. 找出所有 `attention.kind === 'nowhite'` 的任务，重新执行 `resolvePlan`。成功的就清掉 `attention`，挪到队尾。
2. 被放行的任务数大于 0 时，发一条 toast：「N 张等白底图的图已回到队列」。
3. 最后执行一次 tick。

nomatch 的任务不会自动放行，需要用户手动点「重新识别」（对 ① 执行 redo）或指定品类。

### 6.5 输出 `pipeline/output.ts`、`csv.ts`

- 每步产出写进任务目录后，同时复制到：

  ```
  <outputDir>/<outputFolder>/<品类名>/素材图|主图|空白图/<outputBase>.png
  ```

  品类名里的 `\/:*?"<>|` 替换成 `_`。

- `outputBase` 在 ① 完成、第一次确定品类目录时决定：检查同一批、同一品类目录下的 `素材图/<名>.png`、`主图/<名>.png`，以及其他任务已经占用的名字，重名时依次加 `_2`、`_3`。
- 重做产生新结果时，直接覆盖同名文件。
- `识别信息.csv` 放在 `<outputDir>/<outputFolder>/` 下，**每次 ④ 完成都整份重写**：
  - 编码 UTF-8，带 BOM，方便 Excel 直接打开。
  - 列：`原文件名, 品类, 款式, 场景, 关键词, 可定制项, 主图文件`。关键词之间用 `; ` 分隔。
  - 只包含这一批、已经完成 ④ 的任务（界面上「按天导出」仍按 outputDay 汇总当天所有批次）。

## 7. 模版库检查（`library/checks.ts`、`prompts/refcheck.ts`）

### 7.1 配方预览

`GET /library/recipe?cid&sid&tid` 返回：

```ts
{
  images: { no: number | null; role: string; hash: string | null; auto: boolean; required: boolean }[]
  // 例：[{no:1, role:'白底图', hash, required:true}, {no:2, role:'素材图', auto:true}]
  // 自定义模版没有参考图时：[{no:null, role:'参考图', hash:null}, {no:1, role:'素材图', auto:true}]
  prefix: string          // 与实际发送的前置句完全一致（画布部分按白底图实际尺寸或款式比例）
  prompt: string          // 占位符已替换
  scope: string           // 「全局共用 · 所有品类」或「只给「相框·横版」用」（v2 起自定义模版属于款式）
  warnings: string[]
}
```

### 7.2 检查项

`GET /library` 返回的 `checks` 按品类组织：`{ [cid]: { level: 'ok'|'warn'|'error', styles: { [sid]: { level, messages[] } } } }`。按当前选中的模版判断：

- 选中默认模版、但这个款式没有白底图：`error`，提示「缺白底图」。
- 引用检查：提示词里写的「第 N 张」大于这个款式实际发送的图片张数，记为 `warn`，提示「提示词里提到「第 N 张」图片，但这里只会发送 M 张」。
  - 匹配用 `/第\s*([一二三四五12345])\s*张/g`。
  - 实际发送张数 = 素材图 1 张 + 有白底图或参考图时再加 1 张。
- 模版提示词为空：`error`。
- 品类的 `level` 取它所有款式里最差的那个。品类列表上，`error` 显示红点，`warn` 显示黄点。

### 7.3 导入导出 `zip.ts`

- **zip 结构**：`library.json` 和 `images/*`，不打包缩略图（导入时重新生成）。
- **导入前校验**：用 zod 校验 `library.json`，并检查它引用的图片在 zip 里都存在。任何一项不通过，整包拒绝。
- **合并（merge）**：按品类**名称**匹配。名称相同时，用导入的版本覆盖整个品类，但保留本地的 `id`；名称不同的品类追加到末尾。`defaults` 不覆盖。
- **替换（replace）**：先把当前库备份为 `library/backups/library-<时间>.json`（最多保留 10 份），再整体替换，最后清理孤儿图片。

## 8. 图片处理（`image/process.ts`、`prompts/canvas.ts`）

| 函数 | 规则 |
|---|---|
| `describeCanvas(w,h)` | 先算比例 r = w/h，与常见比例逐个比较：1:1、4:3、3:4、3:2、2:3、5:4、4:5、16:9、9:16、2:1、1:2。相差在 3% 以内就取这个常见比例；都不在范围内，就用最大公约数约简后的精确比例。方向：r 在 0.97～1.03 之间为 `square`，大于 1.03 为 `landscape`，否则为 `portrait` |
| `pickApiSize(w,h)` | r > 1.2 取 `1536x1024`，r < 0.8 取 `1024x1536`，其余取 `1024x1024` |
| `ratioToWH("3:2")` | 返回 `[3, 2]`；格式不合法时报错 |
| `toPng(buf)` | 统一转成 PNG，并按 EXIF 方向自动旋转 |
| `capEdge(buf, 2000)` | 长边超过 2000 时等比缩小 |
| `padSquare(buf)` | 用 `extend` 往短边两侧补白（#FFFFFF），**不缩放原图** |
| `capBytes(buf, 9.5MB)` | 超过上限就按 0.85 倍缩小一次，循环直到不超过上限，长边最小缩到 1000 |
| `shrinkForAnalysis(buf)` | 长边缩到 1536，转 JPEG（质量 85）。仍大于 1.5MB 时，质量依次降到 75、65；还不够，就按 0.85 倍缩小，直到不超过 1.5MB |
| `forceSize(buf, w, h)` | `resize(w, h, { fit: 'fill' })` |
| `thumb(buf)` | 长边 320 的 WebP，质量 80 |

## 10. 启动与分发

### 10.1 服务启动（`server/src/index.ts`）

1. 读取 `data/server.json`，里面记录上次运行的 `{ port, pid }`。如果那个 pid 还活着，并且 `/api/health` 能正常响应，说明服务已经在跑：直接打开浏览器，然后退出。
2. 从 3311 开始试端口，被占用就依次往后试，最多到 3320。监听成功后写 `data/server.json`。
3. 加载模版库，清理孤儿图片。
4. 加载全部任务，把 `running` 改回 `pending`，然后 tick。
5. 用系统命令打开浏览器（Mac 用 `open`，Windows 用 `cmd /c start ""`，Linux 用 `xdg-open`）。设置了 `TS_NO_BROWSER` 时跳过。
6. **自动退出**：每分钟检查一次。连续 10 分钟同时满足下面三条，就自动退出：
   - 没有 SSE 连接；
   - 没有 `running` 的步骤；
   - 没有可派发的 `pending` 步骤。

   设置了 `TS_NO_AUTOEXIT` 时不退出。
7. **日志**：写到 `data/logs/YYYY-MM-DD.log`，按天分文件，保留 14 天。

### 10.2 启动脚本

- **`双击启动.command`（Mac）**：
  1. 执行 `xattr -dr com.apple.quarantine`，解除系统对下载文件的隔离。
  2. 依次在 PATH、nvm、fnm、volta、Homebrew 的位置找 Node。版本低于 20.19 时，提示到哪里下载，然后退出。
  3. 如果 `node_modules/sharp` 不存在，执行 `npm install --omit=dev`。
  4. 运行 `node dist/server.cjs`。
  5. 终端窗口保持打开，并提示「关掉这个窗口会停止服务」。
- **`双击启动.bat`（Windows）**：步骤和 Mac 版相同。文件用 UTF-8 编码，开头加 `chcp 65001`，否则中文会乱码。
- **构建**：`npm run build` 依次执行 esbuild 和 vite build。`dist/` 要提交进版本库，这样同事拿到后不需要自己构建。

  - `/v1/images/edits`
  - `/v1/chat/completions`

- **默认行为**：
  - 生图：返回一张纯色 PNG，尺寸取请求里的 `size`，颜色根据 prompt 的哈希值算出。

## 13. 雷区（旧版教训）

## 15. 2026-10-27 变更：批次文件夹、素材图验收、主图贴图方式

原因：用户实际使用时的反馈（2026-10-27）——清空后新图还进同一个文件夹；素材图四周留白、带铝板圆角、细节被重画（Bennett 那张横幅文字被换成了别的）；主图没铺满印刷面、露出金属边，素材图里白色的地方显示成铝板的金属色。

### 15.1 批次文件夹（替换原来「日期-时分」和「有没跑完的图才同一批」）

- 只有点「清空队列」才开新文件夹。图跑完了但没清空，之后加的图继续放进同一个；「清除已完成」不算清空。
- 命名：`主图生成-2026-10-27` → 清空后 `主图生成-2026-10-27-1` → 再清空 `-2`……磁盘上已经有的名字跳过。换了一天从新日期不带序号的名字开始。
- 当前批次存在 `data/batch.json`（`{ day, folder, closed }`），重启后接着用。第一次运行（没有这个文件）时，队列里有今天的图就接着用它们的文件夹。
- 「清空队列」按钮：队列里有图就显示，和运行 / 暂停状态无关。
- 旧版「日期-时分」文件夹（如 `-1530`）的数字不当批次序号；清空后从不带序号的名字找空位。
- 识别信息 CSV：因为「清除已完成」后新图还进同一个文件夹，每批的行另记在 `data/batches/<文件夹>.json`，重写 CSV 时已经移出队列的图的行保留；队列里的图按当前结果更新。

### 15.2 第②步 = 提取 + 素材图验收（不新增步骤）

- 提取请求的前置句：`[Canvas: …] 第一张图片是竞品商品图。` + 换行 + 固定英文约束（`prompts/extract.ts` 的 `EXTRACT_CONSTRAINT`）+ 换行。不可编辑，配方卡和快照里能看到。约束的意思：整个印刷面原样提取、四边铺满；**印在面上的边框、线框、做旧边、锈迹划痕都属于图案，必须保留**；只去掉实体部分（厚度和侧边、圆角外的空白、安装孔和螺丝、透视、反光、阴影、背景），孔和螺丝挡住的地方接着周围的图案补；不重画、不放大、不增删，颜色不变；比例差一点就整体放进画布，不裁不挤文字、元素和边框。
  - 2026-10-27 修改原因：第一版约束写了「不要产品的边框、金属边」，实测 Gingerbread 的锈边和红绿双线框、Family Henry 的红色做旧边都被当成产品边框去掉了，图案还被放大去填画布。
- 验收打开时（设置「素材图验收」，默认打开），提取完这一步回到排队，再占**分析并发**做验收；`job.qc.state = 'pending'` 期间第②步算分析类。重启后接着验收，不重新提取。
- 验收内容，任一项不过即不合格：
  1. **文字（程序判定）**：一个分析请求里让模型分别逐字抄写竞品图印刷面和素材图上的文字（JSON 数组）。程序规范化（NFKC、大小写、标点符号、空白）后按原顺序比对；分行不同不算差异；缺、多、改、顺序调换任何一处都不合格，原因写成「文字变了：原图 X → 素材图 Y」。
  2. **图案元素（模型打分）**：同一次请求给 0～1 相似分和问题清单，低于阈值不合格。默认 0.9：2026-10-27 实测 Bennett（手持斜拍、印刷面只有约 1160×740 像素）房屋、礼物盒等细节明显变样仍有 0.88，另外三张 0.99～1.00，用户确认从 0.8 提高到 0.9。
  3. **颜色（本地判定，2026-10-27 用户要求「竞品图和素材图不能有色差，要原样」，只拦不改）**：同一个验收请求里让模型给出竞品图印刷面的外接框 `print_box`（0～1 比例），程序把这块裁出来、两边各往里收 6%，和素材图缩成同样大小，在 Lab 空间比整体平均色的色差 ΔE（CIE76）和 3×3 分块色差的中位数。整体 ΔE 超过阈值（设置「色差阈值」，默认 5）或分块中位数超过 2 倍阈值就不合格，原因写明方向，如「颜色偏了：整体偏黄、偏艳（ΔE 6.8，超过 5）」。模型没给框时不检查并注明。
     - 阈值依据：用 4 张真实竞品图模拟，提取完全正确时 ΔE≈0；印刷面框偏 2% 时整体 ≤1.2、分块最高 5.1；轻微偏暖 4.4～6.8（一张 16）；饱和度 +25% 为 2.8～4.2。实测后再调。
  4. **四边（模型判断，2026-10-27 新增）**：同一个验收请求里让模型逐条列出竞品图印刷面四边有、素材图没有的内容（`edge_missing`，如「四周的红色做旧边没了」），和素材图四边多出来的东西（`edge_extra`，如金属边、圆角、安装孔、背景）。有任何一条就不合格，原因写「四边少了：…」「四边多了：…」。验收提示词里原来那句「素材图去掉了边框是正常的」已删掉。
  5. **版面（本地判定）**：四边都有 ≥2% 白边、或相对两边都有 ≥5% 白边；≥3 个角是圆角；宽高比和产品比例差 1% 以上。
     - 原来还有一项「四周一圈颜色均匀、和里面明显不同的边框」，2026-10-27 去掉：印在面上的边框（如红色做旧边）和产品金属边从像素上分不出来，会把正确的素材图误判不合格；改由上面第 4 项让模型对照竞品图判断。
     - 比例只在接口画布（3:2、2:3、1:1）能表示产品比例（差 1% 以内）时检查；4:5、3:7 这类跳过，验收结果里注明「接口画布不支持 4:5，未检查比例」（2026-10-27 用户确认，否则这些品类每张都会进需处理）。
- 色彩配置：加图和上传模版图时，带非 sRGB 色彩配置的图（如截屏带的显示器配置「Mi Monitor」）先按配置转成 sRGB 再存。生图和分析模型不认配置，不转的话模型看到的颜色和电脑上看到的不一样（实测那张截屏个别颜色差到 31/255）。
- 两张图都缩小成 JPEG 发送；提示词、两张图、模型原始回复记进 `job.qc.snapshot` / `job.qc.raw`，详情第②步能看到。
- 不合格：不自动重做，进「需处理」（`attention.kind = 'qc'`，第②步 `failed`），显示竞品图和素材图对比、问题清单，按钮「重新提取」（可改提示词，重新提取后再验收）、「仍然使用」（`POST /jobs/:id/qc-accept`，跳过这次验收，记一条日志）、「换品类」。没过验收的素材图不写进输出文件夹，「仍然使用」时才写。
- 验收请求本身出错按分析步骤的重试规则，最终失败进「需处理」（`failed`，提示「素材图验收失败：…」），重试只重做验收。
- 等验收时素材图文件不在了（被删），这一步回到排队、清掉验收状态，按生图类重新提取。
- 关掉验收时不发验收请求，行为和以前一样。

### 15.3 第③步默认模版：本地合成（B）/ AI 贴图（A）

- **B 本地合成**（`image/whiteShape.ts`）：不调 AI。从白底图四边往里找连着的近白背景，剩下的就是产品轮廓；轮廓里被包住的近白小块当作安装孔（连同孔边一圈深色保留白底图原样）。素材图铺满轮廓外接矩形，只在轮廓内显示，边缘抗锯齿；印刷面里不叠加底图的材质、反光。画布是白底图原尺寸，之后照常白底、长边 2000、方图开关、9.5MB 兜底。快照写「本地合成，未调用 AI」，显示用了哪张白底图和素材图；详情里重做就是重新合成（没有提示词可改）。
- **A AI 贴图**：还是原来的请求，前置句后面固定加一段英文约束（`prompts/main.ts` 的 `PASTE_CONSTRAINT`：像不透明贴纸一样覆盖整个印刷面、底材颜色在任何地方都不能透出来、保留安装孔、形状位置背景阴影不变）。只在有白底图时加。
- **自动判断按白底图**（同一个款式的图都一样）：轮廓是正对镜头的矩形（轮廓占外接矩形 ≥97%，允许圆角）或圆形（和内切椭圆重合 ≥97%），产品没贴到图片边缘、图里只有一个物体，且外接矩形比例和款式比例差 **7% 以内**，并且素材图实际的画布比例（接口只有 3:2、2:3、1:1）和外接矩形也差 7% 以内 → B；否则 A。手动选「本地合成」时也做后一项检查，不满足就仍用 AI 贴图并提示。
  - 7% 是 2026-10-27 用户确认的：铝板画「默认」款白底图里的铝板实测外形 1.407（1200×853），款式 3:2，差 6.2%。素材图和外形差 3% 以内等比铺满（居中裁一点），3%～7% 非等比拉伸到外形（不裁切，文字都在）；超过 7% 不走 B，运行时改用 A 并记日志。
- 检测结果按白底图 hash 存进 `library.whiteChecks`（上传白底图时算一次；旧库里已有的白底图第一次用到时算）。
- 每个款式有「贴图方式」：自动（默认）/ 本地合成 / AI 贴图。配方卡上显示现在用的是哪种和自动判断的结果，可以改。手动选本地合成但白底图检测不出轮廓时，仍用 AI 贴图并提示。改了之后对新图生效，已有的图在详情里重做第③步生效。
- 自定义模版、空白图（第④步）不变。

### 15.5 第③步 = 生成主图 + 主图验收（2026-10-27 新增）

原因：用户要求「素材图和主图之间要有检查对比的环节，避免出错」。做法和第②步一样，不新增步骤。设置「主图验收」默认打开，阈值和素材图验收共用（图案相似分 0.9、色差 ΔE 5）。

- **本地合成**：在同一步里本地核对，不发请求。产品外接矩形往里收 6%（避开圆角和安装孔），和铺进去的素材图逐块比颜色，ΔE 超过 2 就不合格（本地合成是确定的，超过就是程序出错了）。
- **AI 贴图**：生成完这一步回到排队，再占分析并发发一次验收请求（素材图 + 主图两张缩小的 JPEG，`prompts/qc.ts` 的 `MAIN_QC_SYSTEM`）：
  1. 文字：模型分别抄素材图和主图印刷面的文字，程序比对，原因写「文字变了：素材图 X → 主图 Y」；
  2. 图案元素：相似分低于阈值不合格；
  3. 贴图：印刷面有没有铺满、有没有透出商品原来的材质颜色（包括素材图里白色的地方），有问题写进 `fill_issues`，原因写「贴图：…」；
  4. 颜色：模型给出主图印刷面的框，程序裁出来和素材图比色差，原因写「主图颜色偏了：整体偏…」。
- 结果存在 `job.mainQc`（字段同 `qc`；`sourceTexts` 是素材图的文字，`patternTexts` 是主图的文字；`mode` 是 local / ai）。没过验收的主图只在任务目录里，不写进输出文件夹；「仍然使用」时才写。
- 不合格进「需处理」（`attention.kind = 'qc'`，`step = 2`），左右对比素材图和主图，按钮「重新生成」（重做第③步）、「仍然使用」、「换品类」。验收请求出错按重试规则，最终提示「主图验收失败：…」。重启后接着验收，不重新生成。
- 测试：`tests/e2e/qc.test.ts` 的 e2e 15（文字变了 / 没铺满进需处理、仍然使用；分数低重做后合格；验收中途重启；本地合成本地核对不发请求；关掉开关不发请求）。

### 15.6 先定印刷面区域，再按区域提取（2026-10-27 新增）

原因：用户问「这个情况在其他品类上也能正确提取吗」。原来是把整张照片交给生图模型，让它自己判断哪些是印的、哪些是产品实体（木框、墙、手），边框被当成产品边框去掉就是这么来的；每个品类还得各写一套规则。用户提出先让 AI 判断图案区域、再按区域提取。先做了低成本验证（4 张铝板画，只发 4 次分析请求）：模型给的四个角 3 张误差约 1%，Bennett 底边往里缩了约 2%；本地往外校正后 4 张的印刷面都完整（做旧边、锈边、线框都在）。

- **第①步**：识别品类的同一个请求里让模型顺便给出印刷面四个角 `print_corners`（0～1 比例，左上、右上、右下、左下；印在面上的边框算印刷面，木框、墙、手、侧边不算；圆角补成直角；斜拍按透视给实际角点）。不多花请求。
- **本地校正**（`image/face.ts`）：四个角要是合法的凸四边形、面积 ≥5%，否则当作没给。每条边在外侧 3.5%（占短边）以内找最外面的强边缘，取中位数，再多留 0.4% 余量。**只往外挪、不往里缩**：验证时两个方向都找，把 Gingerbread 底边吸到了锈边内侧那条线上，切掉一窄条锈边。带一丝背景交给生图模型去掉，比切掉图案安全。结果存在 `job.face`（`ai` 模型给的、`corners` 校正后的、`moved` 各边外移像素、`size` 印刷面在原图里的大小）。
- **第②步**：有 `job.face` 时，按款式比例把印刷面拉正成 `face.png`（长边取印刷面在原图里的长边，不超过 2048，不凭空放大），只把它发给生图模型；前置句的图片角色写「从竞品图裁出并拉正的商品印刷面」，约束换成 `FACE_CONSTRAINT`（这是已经裁好的印刷面，原样做成平面印刷稿；印着的边框、做旧边全部保留；只去掉边上残留的背景和手指、圆角外的背景、侧边、安装孔螺丝、反光阴影）。没有 `job.face` 时照旧按整张竞品图提取。
- **素材图验收**：有拉正后的印刷面时拿它对照（提示词说明第一张是裁好拉正的印刷面，边上残留的背景、手指不算）。两张图对齐，颜色直接整张比较，不用模型给的框。
- **界面**：详情第①步在竞品图上画出提取区域（实线）和 AI 原始位置（虚线），写明往外校正了多少；第②步配方卡的第 1 张图是「印刷面」；看大图里多一张「印刷面」；「需处理」里素材图验收的对比改成印刷面对素材图。
- **审查后补的规则**（2026-10-27）：
  - 四个角不管模型按什么顺序给（逆时针、从右上开始），都整理成左上起顺时针；顺序错了拉正出来会镜像或转 90 度，而验收对照的也是这张错图，拦不住。
  - 模型给成像素坐标时，按它看到的缩小图换算；四个角不合格时记日志，按整张图提取。
  - 每条边用采样点拟合真实边缘的直线，两头各自往外补（只外不内），模型给的边是斜的也能补回来；原来整条边取一个中位数平移，斜边还是会切掉边框。
  - 量出来的印刷面宽高比和款式比例差 1.4 倍以上（方向反了、框错了）不硬拉，这次按整张竞品图提取并记日志。
  - 大图先缩小再定位、拉正，避免全尺寸解码占几百 MB 内存。
  - 框错了的出口：详情第②步重做时勾选「按整张竞品图提取」，清掉 `job.face`。重做时删掉旧的 `face.png`。
- **还解决不了的**：原图分辨率低时（Bennett 印刷面只有约 1179×755 像素）小细节模型仍会补画；毛毯褶皱、花园灯曲面，四个角拉不平；亚克力挂件异形外形四个角框不住，以后单独处理。
- 测试：`tests/unit/face.test.ts`（角点校验；往里缩 2% 时往外补到外缘、红边完整；已经在外面时不往里缩；斜拍拉正）；`tests/e2e/qc.test.ts` 的 e2e 16（给四个角时只发拉正后的印刷面、验收拿印刷面对照；四个角不合法时退回整张图）。


## 16. 2026-10-29 变更：提取不许往外延伸、边框外延检查、品类提示词分层

起因：用户 10-28 实测，搭在扶手椅上的拼格毛毯（Amelia）提取出来左、右、下各多出半圈格子，素材图验收却给了 0.99 分通过；用户只好手动改图。

- **分层原则**：所有品类都会犯的错放进不可编辑的固定约束；材质特有的情况（软布折叠、包边，帆布画包边侧面、木框）放品类的「单独设置」提取提示词。不全写进全局，是因为规则会互相冲突（铝板画「边上印的都保留」与毛毯「折过去的格子不是新的一排」），改一次可能把已经调好的品类弄坏。
- **固定约束**：`EXTRACT_CONSTRAINT`、`FACE_CONSTRAINT` 末尾都加 `NO_EXTEND`：不许把图案往外延伸，不许多一排、一列格子或一圈边框，画布边上不许出现被切掉一半的元素，每边重复元素的个数和原图一致。
- **品类提示词**（写进用户模版库，不进代码）：毛毯写明软布会折过扶手、往下垂，要还原成平铺；最外面的细包边就是画布边缘；折过去的部分还是同一圈边框格子，每边格子数和顺序与照片一致。帆布画写明只要正面，侧面包过去的画面、木框、外框、卡纸不要。
- **边框外延检查**（`BORDER_SYSTEM`，第②步验收时单独发一次分析请求，和原验收同时发）：让模型数两张图四条边的格子，并写出素材图有没有被画布切掉一半的格子、有没有多一排。写进原验收提示词里实测 4 次都漏看（0.98～0.99），单独问 4 次都抓到，5 张合格图没有误拦。格子个数每次数得不一样，只当参考，判定只看 `pattern_partial`。有边框的图模型要想 40～160 秒，超时放宽到 180 秒；重试单独计数（最多再试一次），不占这一步的尝试次数；请求没成功写明「没检查成」，不拦。结果存 `qc.border`，详情第②步显示「边框外延」一行。
- **实测结论**：新提示词重提 3 张毛毯、2 张相框，原来合格的没有退步。Amelia 这张（毯子两侧、底边折到看不见的地方，只能按整张图提取）三次都还会多出半格或一排，提示词收不住；现在能被边框外延检查拦进「需处理」。
- 测试：`tests/unit/prompts.test.ts`（两种约束都以 `NO_EXTEND` 结尾）；`tests/e2e/qc.test.ts`（多出半圈格子进需处理；检查请求失败不拦）。模拟服务按系统提示词里的「边框外延检查助手」识别这类请求，只消费 `border` 队列，不吃 `chat` 队列。

## 17. 2026-10-29 变更：子体 SKU、输出文件按 SKU 命名、专属号统一

用户要求：没有产品 SKU 推荐；导出的图直接按 SKU 命名。规则由用户给出并确认。

- **格式**（`server/src/pipeline/sku.ts`）：`店铺缩写-材质缩写 + 年份末位 + 地区标识 + 月日 + 专属号 + 当天序号两位`，如 `HJ-mtfl671029101`；序号过 99 自然变三位。
- **当天序号**：每个品类（按材质缩写）每天各自从 01 起，换一天从 01 起（用户选的）。记在 `data/sku.json`（只留当天），发出去不收回：删图、清空队列、换批次、重启都接着排，和变体占号一致。分配时跳过别的任务已经用了的、输出文件夹里已经有同名文件的。
- **什么时候发**：任务第一次定下品类（第①步完成、手动指定品类）时发；换了品类重发；同一品类重做、品类改名不换号。品类没填材质缩写不发，文件名照旧用原图名。
- **文件名**：`job.outputBase` 有 SKU 就用 SKU（主图、素材图、空白图同名）。
- **设置**：新增 `sku: { store: 'HJ', region: '7' }`；专属号就是原来的 `parent.creatorMark`（用户确认「建议新建父体」的创建人标识和子体 SKU 的专属号是同一个），界面上移到设置「SKU 命名」一组，父体组里只显示。用户的值从 5 改成 1。
- **模版库**：品类加 `skuCode`（材质缩写，旧库读入补 null，不升版本），只允许字母、数字和 `-`。用户的缩写从飞书父体前缀去掉专属号推出、用户确认：毛毯 mtfl、帆布画 xkfb、铝板画 lbh、庭院灯 cn-tyntyd、亚克力挂件 cn-yklgj。「花园灯」按用户要求改名为「庭院灯」（飞书标签页同名）。
- **识别信息表 / CSV**：表里有 SKU 时多一列 SKU（可复制）；CSV 第 2 列固定是 SKU。之前存下的移出队列的行（`data/batches/*.json`）没有这一列，读入时在第 2 列补空（`SavedRow.v = 2` 标记新格式）。
- 测试：`tests/unit/sku.test.ts`、`tests/e2e/sku.test.ts`（发号、文件名、清空和重启后接着排、不填缩写用原名）、`tests/unit/output.test.ts`（旧行补 SKU 列不错位）、`tests/web/info-table.test.ts`、`tests/unit/settings-api.test.ts`。

## 18. 2026-10-29 变更：提取分两种情况、主图不限制比例、素材图按精确比例

起因：用户 10-29 实测帆布画主图顶上长出一块凸起；毛毯仍提取不对。用户要求：竞品图完整不变形的框选出来，放在场景里有变形的让生图 AI 自己提取矫正（提示词写完善）；AI 贴图不要限制比例。

- **第①步加 `print_flat`**：同一个识别请求里让模型判断印刷面是否完整、平整（斜拍也算平整）。`false` → `job.deformed = true`，不取四个角、不拉正（四个角框不住搭着的软布，拉正后混进椅子和地毯、毯子还是斜的）。拿不准按 false。实测：帆布画判 true，两张搭在扶手椅上的毛毯判 false。
- **第②步三种方式**（`buildExtractRequest` 的 mode）：`face` 拉正后的印刷面 + `FACE_CONSTRAINT`；`scene` 整张图 + `SCENE_CONSTRAINT`（新：还原成平铺正面的印刷稿，拉直褶皱和透视，去掉背景家具手，被遮住的只按看得见的图案规律补，格子边框只一圈、每边格子完整）；`photo` 没框出印刷面的整张图 + `EXTRACT_CONSTRAINT`。模版库提取预览两种前置约束都显示。
- **素材图尺寸按款式精确比例**（`exactSize`：长边 1536，16 的倍数）。原来只有 1536x1024 / 1024x1536 / 1024x1024 三种，4:5 被套成 1024x1024，和前置句「4:5 竖版」打架。中转站接受任意尺寸（实测 1024x1280、1456x1088）。版面检查因此 4:5 也查比例，比 1:2.5 还细长的不查。
- **主图有第一张图（白底图、参考图）时不写画布句、size 传 `auto`**：实测原因是帆布画白底图约 4:3，被要求出 3:2，模型重新构图画走样；同一套提示词、同一个模型，传和白底图一致的尺寸或 auto 都没有凸起。没有第一张图的自定义模版仍按主图比例 / 款式比例精确出图。
- **模型实测**（毛毯整张图 + 场景约束 + 4:5）：gpt-image-2 两次都多出边；gpt-image-2.5-flare 一次接近用户手改版、一次多一列；sunburst 一次多一列。贴图三个模型都没问题。样本少，没有换默认模型，告诉用户可以在设置里改成 gpt-image-2.5-flare 试用。
- **还没解决**：有变形的竞品图 AI 提取仍是时好时坏；边框外延检查在新图上漏过两次，靠不住。
- 测试：`tests/unit/prompts.test.ts`（精确尺寸、scene 前置约束、主图 auto）、`tests/e2e/qc.test.ts`（print_flat=false 走整张图 + 场景约束）、`tests/e2e/pipeline.test.ts`、`tests/unit/library-api.test.ts`、`tests/unit/pattern-qc.test.ts` 按新规则更新。模拟服务 size=auto 时照第一张输入图出图。
